I was reading my build output when I noticed the SEO plugin talking about breadcrumbs. Breadcrumbs? My site doesn't have breadcrumbs. There's no little `Home › Blog` trail anywhere.

Except it turns out my site absolutely had breadcrumbs. Every single page was shipping them. I just couldn't see them, because they were only for robots.

## The invisible kind

Since the [SEO overhaul](/blog/agent-ready-seo-with-the-yoast-founders-tools/), every page here carries a block of JSON-LD in its head: machine-readable data that describes the page to search engines. Part of that block is a `BreadcrumbList`, which spells out where the page lives in the site's hierarchy:

```json
{
  "@type": "BreadcrumbList",
  "itemListElement": [
    { "position": 1, "name": "Home", "item": "https://jpshlk.com/" },
    { "position": 2, "name": "Blog", "item": "https://jpshlk.com/blog/" },
    { "position": 3, "name": "Learning Astro" }
  ]
}
```

This is what lets Google show `jpshlk.com › Blog › Learning Astro` under a search result instead of a raw URL. Useful! But it created a funny situation: search engine crawlers had better navigation on my site than actual humans. Google's own guidelines also nudge you to only mark up content that's visible on the page, and mine was the opposite of visible.

So the fix wasn't "add breadcrumbs." The breadcrumbs existed. The fix was making them visible.

## One source, two outputs

The rule I gave myself: the visible trail and the JSON-LD must come from the same data, so they can never disagree. The crumb-building moved into two small exported helpers, and now both consumers call them:

```ts
// src/lib/schema.ts
export function postCrumbs(post: Post): BreadcrumbItem[] {
  const url = postUrl(post);
  return breadcrumbsFromUrl({ url, siteUrl: SITE.url, pageName: post.data.title });
}
```

The JSON-LD builder uses `postCrumbs(post)` for its `BreadcrumbList`, and the new `Breadcrumbs.astro` component takes the same array as a prop:

```astro
<article class="pt-10" data-pagefind-body>
  <Breadcrumbs crumbs={postCrumbs(post)} class="mb-6" />
```

Same function, same inputs, two representations. There is no way to update one and forget the other, because there's nothing to update twice.

## Two decisions that kept it small

**The visible trail only shows ancestors.** On a post you see `Home › Blog`, both clickable, and that's it. The current page's name isn't repeated as a dead crumb, because the title is sitting right there in giant letters. The JSON-LD still includes the current page (search engines want the full trail), and the component just slices it off the end.

**Only deep pages get one.** Posts, project pages, and tag pages. Top-level pages like `/about/` would show a trail consisting entirely of `Home`, and the logo in the header already does that job. A breadcrumb with one crumb is just clutter.

## The bug that hadn't happened yet

Sharing one data source immediately paid for itself. While wiring it up, I noticed the crumb names for intermediate segments were generated by title-casing the URL slug. For `/tags/web-development/` that gives you "Web Development." Great. For `/tags/ios/` it gives you "Ios." 🤦

Nobody had ever seen "Ios" because the tag segment only becomes an *intermediate* crumb on paginated tag pages, and my iOS tag doesn't have enough posts to paginate yet. The bug was sitting there waiting for me to write a few more Shortcuts posts. Now the tag page passes its real display name into the crumb builder, the JSON-LD and the visible trail both get "iOS", and future me is spared a very confusing bug report from a stranger.

## The boring details that matter

The component itself is tiny, but the details are where breadcrumbs usually go wrong:

- It's a `<nav aria-label="Breadcrumb">` wrapping an ordered list, which is the pattern screen readers expect. The `›` separators are `aria-hidden` so they aren't read aloud.
- The links render as plain paths like `/blog/`, not full URLs. The crumb data carries absolute `jpshlk.com` URLs, and rendering those directly would mean clicking a breadcrumb on a preview deploy teleports you to production.
- It carries `data-pagefind-ignore` so site search doesn't index the words "Home Blog" on every single page.

If you want to see where the component sits in the page structure, the map at [how this site works](/how-this-site-works/) has it.

The takeaway travels well beyond breadcrumbs: when the same fact lives in two places, don't sync it, derive it. The robots and the humans now read from the same map. 🤙
